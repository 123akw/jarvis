# 个人微信桥接完整闭环设计

## 目标

在现有 J.A.R.V.I.S. 网站与 macOS 桌面端中完成个人微信桥接：用户可生成二维码、扫码确认、保持登录、通过微信向贾维斯发送私聊消息并收到回复。功能需部署到 `https://jws.gkgeek-set.cn`，并通过真实扫码和消息往返验收。

## 范围

- 网页端提供个人微信入口、接入说明、二维码、连接状态、错误提示和断开操作。
- 桌面设置页复用相同服务端接口，提供二维码、连接状态和断开操作。
- FastAPI 进程内管理扫码、凭据、长轮询、Agent 调用和微信回复。
- 服务重启后使用持久化凭据自动恢复桥接。
- 线上安装新增依赖、更新静态资源并重启现有 `jarvis-web.service`。
- 通过线上二维码完成真实扫码、消息回复和服务重启恢复验证。

以下内容不在本轮范围：群聊回复、图片或语音消息、营销群发、多微信账号管理、独立网关的进程管理界面。

## 方案选择

采用 FastAPI 服务内置桥接。

该方案沿用当前实现方向：网站、桌面端与桥接共享一套状态和三个受登录保护的 API；线上只维护现有 `jarvis-web.service`。相比独立网关进程，它不需要额外的进程间通信、状态同步或部署单元。仓库中的 `wechat/ilink_gateway.py` 继续保留为高级用户备用入口，但不参与网站状态，文档明确禁止与内置桥接同时使用同一个微信凭据。

## 组件边界

### `jarvis/wechat.py`

作为唯一微信桥接状态机，负责：

- 获取二维码并生成可直接显示的 SVG data URI。
- 轮询扫码状态并持久化 `bot_token`。
- 运行唯一的消息长轮询工作线程。
- 从私聊文本中提取消息并调用贾维斯 Agent。
- 将回复按安全长度分段发回原联系人。
- 处理断开、二维码过期、网络波动、凭据失效和服务重启恢复。

状态对外统一为 `idle`、`loading`、`waiting`、`connected` 和 `error`。状态响应可包含 `qr_uri`、`error`、`since`，但绝不包含微信 Token。

### `jarvis/server.py`

提供受现有登录机制保护的接口：

- `GET /api/wechat/status`
- `POST /api/wechat/connect`
- `POST /api/wechat/disconnect`

接口只调用状态机，不在请求线程执行扫码或消息长轮询。应用启动时尝试恢复已保存的微信凭据，应用退出时通知后台工作线程停止。

### 网页端

HUD 顶栏增加个人微信入口。点击后打开 `WeChatConnect` 弹窗；弹窗每两秒读取状态并显示接入说明、加载态、二维码、连接成功、超时或错误信息。二维码过期后可重新生成，关闭弹窗不影响服务器桥接。

### macOS 桌面端

设置页增加个人微信区域，复用同一组 API 和桌面端已有的 `X-JWS-Token` 鉴权。打开设置时开始刷新微信状态，离开设置时停止定时器，避免重复轮询。桌面端不保存微信 Token，也不启动本地微信网关。

### 独立网关

`wechat/ilink_gateway.py` 继续作为命令行备用方案。文档将内置桥接列为默认方式，并说明不要同时运行两套桥接，否则同一凭据可能发生重复拉取或重复回复。

## 数据流

1. 已登录用户在网页或桌面端点击“生成二维码”。
2. 服务端向 iLink 获取二维码标识和扫码内容，进入 `waiting` 状态并启动扫码轮询。
3. 用户使用专用微信小号扫码并在手机端确认。
4. 服务端取得 `bot_token`，以 `0600` 权限写入 `JARVIS_DATA_DIR/wechat_token`，进入 `connected` 状态并启动唯一消息轮询线程。
5. 收到私聊文本后，服务端为联系人派生 `wx-<联系人>` 记忆线程，调用现有 LangGraph Agent。
6. Agent 回复被转换为纯文本并按安全长度拆分，通过 iLink 发回原联系人。
7. 用户主动断开时，服务端停止轮询、删除 Token 并返回 `idle`。
8. 服务重启时如发现 Token，则自动进入 `connected` 并恢复轮询；若 iLink 返回未授权，删除 Token 并要求重新扫码。

群聊和非文本消息默认忽略。

## 并发与生命周期

- 使用锁保护共享状态、代次标识和工作线程引用。
- 每次新建二维码递增代次；旧扫码线程即使延迟返回，也不得覆盖新一代状态。
- `connect` 幂等：已连接时直接返回当前状态，正在生成或等待扫码时不重复创建任务。
- 消息轮询在任意时刻最多运行一个实例。
- `disconnect` 使当前代次失效并设置停止信号，旧线程随后退出。
- 网络请求使用独立客户端并在工作线程退出时关闭。

## 错误处理

- 二维码接口失败：进入 `error`，返回可读提示并允许重试。
- 二维码超时：回到 `idle`，提示重新生成。
- iLink 响应缺少必要字段或 JSON 无效：作为协议错误显示，不泄露响应中的敏感内容。
- 消息长轮询网络波动：短暂退避后继续，不改变连接状态。
- Token 未授权：删除持久化 Token，停止轮询并回到 `idle`。
- Agent 调用失败：向联系人返回简短兜底提示，保持桥接在线。
- 单条回复发送失败：记录错误并继续轮询，避免整个桥接退出。

## 安全

- 微信 Token 只存在于服务器数据目录，文件权限为 `0600`。
- 状态 API 和操作 API 继续使用现有 Cookie 或 `X-JWS-Token` 鉴权。
- 前端不记录微信 Token，不把 Token 写入日志、HTML 或构建产物。
- 默认忽略群聊；界面明确建议使用专用小号并提示第三方接入风险。
- 线上发布和回滚均保留 `/var/lib/jarvis`，不随代码切换删除用户数据或微信 Token。

## 测试与验收

### 自动化测试

- 微信 API 未登录访问返回 `401`。
- 成功获取二维码后状态为 `waiting`，并返回可显示的二维码 URI。
- 重复连接不会创建第二个扫码任务。
- 扫码确认后 Token 持久化，状态进入 `connected`。
- 私聊文本进入联系人独立记忆线程并发送回复。
- 群聊和非文本消息被忽略。
- `401` 使 Token 删除并回到重新扫码状态。
- 主动断开停止后台任务并删除 Token。
- 服务启动时可从 Token 恢复连接。
- 旧扫码线程不能覆盖新代次状态。

运行 Python 全量测试和 React 生产构建；检查桌面端脚本语法及设置页二维码区域。使用浏览器验证网页入口、弹窗状态和二维码显示。

### 线上验收

1. 记录上线前 Git 提交、服务状态和首页静态资源版本。
2. 安装项目依赖并部署新代码与前端构建产物。
3. 重启 `jarvis-web.service`，验证服务为 active、首页和 `/api/session` 正常。
4. 登录网站，生成二维码，确认线上状态接口返回 `waiting`。
5. 将二维码显示在网站对话框，并按用户需要另存到本机桌面。
6. 用户扫码确认，验证状态变为 `connected`。
7. 用户从另一个微信联系人向桥接账号发送测试文本，确认收到贾维斯回复。
8. 重启线上服务，确认状态自动恢复且第二条测试消息仍可往返。
9. 验证主动断开后 Token 删除且状态回到 `idle`；如需保留在线状态，则在验收结束前重新扫码连接。

## 发布与回滚

生产环境为 `root@1.12.67.169:/opt/jarvis`，由 `jarvis-web.service` 运行，Nginx 将 `jws.gkgeek-set.cn` 反向代理到 `127.0.0.1:7789`。

发布前创建可识别的代码备份点，保存当前提交 `01eb549` 作为基线；不修改 `/var/lib/jarvis`。发布包括安装 `segno`、同步代码与构建产物、重启 systemd 服务和执行健康检查。

若依赖安装、服务启动、登录、状态接口或首页检查失败，则把 `/opt/jarvis` 代码恢复到发布前备份点，重新安装基线依赖并重启服务。回滚后再次检查 systemd 和网站健康状态。

## 完成标准

- 网页和桌面端均能生成并显示同一个服务端桥接状态。
- 线上真实扫码后显示已连接。
- 微信测试消息能够触发贾维斯并收到回复。
- 服务重启后连接可自动恢复。
- 主动断开和 Token 失效能够安全回到重新扫码状态。
- 自动化测试、前端构建、线上健康检查全部通过。
